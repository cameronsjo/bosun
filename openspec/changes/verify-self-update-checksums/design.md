## Context

Bosun uses `github.com/creativeprojects/go-selfupdate` v1.6.0 to discover a
stable GitHub release, select the archive matching the runtime OS and
architecture, decompress it, and replace the current executable. The updater is
currently constructed without a `Validator`.

`.goreleaser.yaml` produces `checksums.txt` with SHA-256 entries. The live
v0.40.7 release contains that manifest plus exactly these archives:

- `bosun_0.40.7_darwin_amd64.tar.gz`
- `bosun_0.40.7_darwin_arm64.tar.gz`
- `bosun_0.40.7_linux_amd64.tar.gz`
- `bosun_0.40.7_linux_arm64.tar.gz`

The published manifest uses GoReleaser's `<64 lowercase hex><two spaces><asset
name>` format and covers all four archives. go-selfupdate's
`ChecksumValidator` consumes that format, associates the validation asset while
detecting the release, and validates the downloaded compressed archive before
decompression and executable replacement.

PR #602 separately propagates Cobra's context through the update path and turns
command failures into non-zero results. This proposal depends on that behavior
but does not duplicate its general error-handling work.

## Goals / Non-Goals

- Goals: verify the exact archive selected for the current platform; bind the
  archive and checksum manifest to one detected release; make every
  checksum-contract or asset-download failure fail closed; keep the old
  executable untouched before verified replacement begins; test without GitHub
  or another network service; state the trust boundary accurately.
- Non-Goals: sign `checksums.txt`; verify Sigstore or SLSA attestations; change
  release selection or archive naming; add platforms; redesign go-selfupdate's
  atomic replacement; add an offline checksum cache or automatic retry policy;
  harden `scripts/install.sh`; add an insecure bypass.

## Decisions

### Use go-selfupdate's single-manifest validator

Construct the existing updater with
`&selfupdate.ChecksumValidator{UniqueFilename: "checksums.txt"}`. This keeps
release discovery, private-source download behavior, decompression, and atomic
replacement inside the existing library and validates the compressed release
asset that GoReleaser hashes.

The implementation will not maintain a second checksum parser. Missing
`checksums.txt` is rejected during release detection. A missing or malformed
selected-archive entry, malformed content encountered before that entry, or a
digest mismatch is rejected after download and before decompression or
replacement. No failure falls back to an unchecked install.

Detection captures the selected archive asset and the uniquely named checksum
asset from one `SourceRelease`. Installation must pass that exact detected
release object to `UpdateTo`; it must not redetect the latest release or select
a replacement asset between downloading the archive, downloading its manifest,
and validating it. If either captured asset disappears or its download fails,
the attempt fails closed instead of switching releases or assets.

The built-in validator scans GoReleaser's two-space SHA-256 lines and returns the
first entry whose filename exactly matches the selected archive. It does not
continue parsing unrelated lines after that match. Runtime code will not add a
second parser with different ambiguity rules because later unrelated entries do
not affect the selected archive's digest. The release-contract check instead
validates the whole generated manifest and ensures GoReleaser emits exactly one
well-formed entry for every supported archive.

### Treat same-release checksums as integrity, not publisher authentication

The archive and `checksums.txt` are fetched as assets of the same GitHub release
through the configured GitHub source. This detects corruption, truncation,
asset/manifest mix-ups, and archive modification when the separately fetched
manifest remains intact.

Because the manifest is not cryptographically signed by a key embedded in
Bosun, it does not defend against an attacker who can replace both GitHub
release assets or compromise the release publisher. Sigstore/SLSA verification
and signed checksum manifests remain separate future work. Documentation must
not describe this change as release authenticity or signature verification.

### Preserve release and platform compatibility without a fallback

Stable semantic-version selection, prerelease exclusion, and OS/architecture
matching remain unchanged. The supported release tuples are darwin/amd64,
darwin/arm64, linux/amd64, and linux/arm64, with archive names generated by the
existing GoReleaser template.

Version comparison also remains unchanged: an installed stable version equal
to or newer than the latest eligible stable release is not reinstalled or
downgraded, while the development version continues to treat the latest stable
release as eligible. Checksum validation does not create a path to prereleases
or unsupported platform assets.

The first Bosun release containing this implementation will also contain
`checksums.txt`, so no configuration or state migration is required. Once a
checksum-aware binary is installed, a latest release that omits the manifest or
its selected archive entry is intentionally unavailable to `bosun update` until
the release is repaired. Older Bosun binaries retain their historical behavior
until upgraded; this change does not retroactively secure those downloads.

`bosun update --check` continues to avoid downloading archive and checksum
bytes. It validates only that detection found the selected platform archive and
the uniquely named `checksums.txt` asset on the same release; it does not parse
or validate checksum content until installation downloads the assets. It may
therefore fail while inspecting metadata when the required manifest asset is
absent, because such a release is not installable safely.

### Surface verification failures through the command boundary

Checksum failures propagate with their wrapped cause through `internal/update`
and the Cobra `RunE` path established by PR #602. The command returns non-zero,
does not print the successful-update message, and retains the underlying error
identity where the source exposes one. Its message identifies the failed
download or validation stage and the relevant selected archive or
`checksums.txt` asset without requiring callers to match one exact full string.
The updater must not print an unchecked-success warning or silently report that
the current version is latest.

An archive-download failure, checksum-download failure, cancellation, or
post-detection disappearance is terminal for that invocation. Bosun does not
use a cached manifest, retry automatically with unchecked bytes, or fall back
to another release. An operator may rerun the command, which performs a fresh
detection and repeats the complete verified flow.

### Test the real validator and replacement boundary without a network

Tests will provide an in-memory `selfupdate.Source` containing a synthetic
release, a small platform-named tar.gz archive, and `checksums.txt`. The success
case exercises release detection, archive download, checksum validation,
decompression, and replacement of a temporary sentinel executable.

Table-driven failure cases will omit the checksum asset, provide a malformed
selected entry or malformed content before any selected entry, omit the selected
archive entry, and provide a wrong digest. Each case will assert the expected
wrapped validation error, no success result, and byte-for-byte preservation of
the sentinel executable. Platform-selection tests will cover all four published
tuples. Check-only tests will assert that asset-presence metadata is checked
without downloading either asset.

Additional deterministic cases will fail archive and checksum downloads after
detection, mutate the source's latest release after detection, and exercise
cancellation. They will prove that `UpdateTo` consumes the originally captured
asset identities, preserves wrapped errors, and never enters replacement for a
failed attempt. Version cases will pin equal/newer stable, development,
prerelease, and unsupported-platform results inherited from the current
updater, including the existing distinction between check-only and install
commands when no suitable asset is found.

Checksum validation finishes before go-selfupdate enters decompression and
replacement. A validation failure therefore requires no rollback and leaves the
sentinel untouched. Once validation succeeds, the library's existing atomic
replacement and rollback behavior remains the recovery boundary and is not
changed by this proposal.

## Risks / Trade-offs

- A broken release manifest blocks self-update even when the archive itself is
  valid. This is the intended fail-closed behavior; the release must be repaired
  instead of asking users to bypass verification.
- Self-update has no offline checksum cache. A transient asset download failure
  rejects that invocation; a later explicit rerun starts a fresh verified
  attempt.
- The implementation relies on go-selfupdate's line-oriented checksum parser,
  which stops after the exact selected filename. Focused fixtures cover that
  selection behavior; a separate release-contract check validates the complete
  generated manifest and catches drift from GoReleaser's current two-space
  SHA-256 format.
- Same-release checksums do not provide independent authenticity. Documentation
  will keep this boundary visible and avoid overstating the control.

## Migration Plan

1. Merge and label this spec only after strict validation and review converge.
2. Implement after PR #602 lands, or rebase while preserving its context and
   non-zero error behavior.
3. Run deterministic updater/command tests, the release-contract check, full
   repository quality gates, and a GoReleaser snapshot verification.
4. Ship through the normal release pipeline and confirm the new release exposes
   `checksums.txt` with entries for every archive before exercising self-update.
5. If release metadata is incomplete, repair or republish the release; do not
   add a runtime bypass. Operators may use a separately verified manual or
   package-manager installation path for recovery.
